# 大雁养老 - 产品需求设计文档 v4.0

> **核心定位**：大雁养老是**养老服务权益平台**，核心产品是「养老权益」，由保险公司（渠道）采购后赠送给其客户。平台提供权益管理、场景活动、内容素材、养老管家服务等能力，帮助保险行业通过养老权益增强客户粘性和销售转化。
>
> **重要说明**：
> - 大雁的核心商品是**权益**，不是保险。保险本身只是记录（权益函可能关联保险公司保单）。
> - 代理人和客户都依附于渠道，不存在客户自主购买权益的场景。
> - 权益采购只发生在两个场景：①渠道（保险公司）对公采购 ②渠道项下的代理人通过专门商城个人采购。
> - 权益寄送给渠道/代理人后，由他们自行赠送给客户，大雁把控不到赠送过程，只能监控客户的激活流程。
> - 代理人不进行产品分销，不涉及代理人佣金逻辑，系统仅为工具支持。
> - 养老管家通过电话或企业微信与客户对接服务，系统内由管家操作状态流转。
>
> **架构基础**：以《大雁养老服务权益平台数据库设计方案（最终版）》为真相源，17个业务域数据表。所有功能需求、业务流程、数据模型均与数据库设计保持对应。

## 一、整体业务架构

### 1.1 商业模式全景

```
┌─────────────────────────────────────────────────────────────────┐
│ 大雁养老服务权益平台                                                     │
│     ↓ 三大服务形态                                               │
│ ┌──────────┐ ┌──────────┐ ┌──────────┐                          │
│ │ 权益包装 │ │ 场景活动 │ │ 系统支撑 │                          │
│ └────┬─────┘ └────┬─────┘ └────┬─────┘                          │
│      │              │              │                              │
│ ┌────┴──────────────┴──────────────┴────┐                        │
│ │ 养老管家服务层                        │ ← 服务交付层           │
│ │ （需求收集→方案定制→全程安排→回访品控）│                        │
│ └────────────────┬────────────────────┘                          │
│                  │                                              │
│ ┌────────────────┴────────────────────────┐                      │
│ │ 供应商/养老机构资源层                   │ ← 资源供给层           │
│ └──────────────────────────────┬─────────┘                      │
└─────────────────────────────────┼──────────────────────────────┘

采购端（对公/代理人个人）                 服务端（客户激活后触发）
┌──────────────┐                       ┌──────────────┐
│ 渠道（保险公司）│ ← 对公采购权益 →      │ 客户/老人    │
│ 代理人         ← 商城个人采购 →        │ 家庭成员     │
│ 分销商（外部商务）← 渠道归属记录        │              │
└──────┬───────┘                       └──────┬───────┘
       │                                      │
       │  权益寄送（系统外）                     │ 权益激活（系统可追踪）
       │  → 渠道/代理人自行赠送给客户 →          │  → 触发管家服务流程 →
```

**商业模式核心要点**：

| 维度 | 说明 |
|------|------|
| 价值主张 | 为保险行业提供差异化的养老服务权益，增强保险产品竞争力和客户粘性 |
| 收入来源 | 渠道对公采购权益费用、代理人商城采购费用、场景活动费用、平台服务费 |
| 核心壁垒 | 养老机构资源整合能力、养老管家专业服务能力、系统化运营能力 |
| 增长飞轮 | 更多渠道 → 更多权益采购 → 更多养老机构入驻 → 更好服务 → 更多渠道 |

### 1.2 四大业务支柱

1. **权益包装**：将养老服务（机构入住、日间照料、居家护理等）打包为不同等级的养老权益产品，保险公司/代理人采购后赠送给客户
2. **场景活动**：依托养老机构场地资源，为保险公司/代理人策划并组织客户活动（参观体验、健康讲座、亲子互动等），促进保险销售转化
3. **系统支撑**：提供完整的渠道对接系统（养老保典面向代理人、客户端面向客户），通过H5页面或API接口实现功能嵌入；内容由大雁生产，渠道自行配置下游两端展示哪些内容
4. **管家服务**：客户通过权益激活发起服务使用需求，由养老管家通过电话/企微全程跟进「需求收集→方案定制→全程安排→回访品控」四步标准流程

### 1.3 核心角色定义

| 角色 | 系统标识 | 职责描述 | 关键能力 |
|------|---------|----------|----------|
| **平台运营方** | organ（大雁养老） | 平台整体运营、资源管理、规则制定、服务质量管控、内容生产 | 全局管理、数据分析、运营决策 |
| **养老管家** | butler | 服务平台，通过电话/企微对接客户，提供专业服务（需求评估、方案定制、全程安排、回访品控） | 专业评估、方案制定、资源协调、客户沟通 |
| **供应商** | supplier | 养老机构的运营方，提供场地和服务；**独立系统角色**（Supplier 系统，见 §3.4），不归属渠道端 | 机构运营、服务提供、资源管理 |
| **渠道** | channel | 保险公司等合作方，对公采购权益、组织活动、配置下游内容展示 | 客户资源、销售渠道、品牌推广 |
| **分销商** | distributor | 外部商务合作方，为平台带来渠道资源；**独立系统角色**（Distributor 系统，见 §3.5），不是渠道的子角色。系统仅记录哪些渠道由某分销商引入，用于结算佣金 | 渠道拓展、商务推广 |
| **代理人** | agent | 保险公司的销售人员，可通过商城采购权益赠送给客户，通过平台工具增强保险销售 | 客户维护、权益赠送、活动组织 |
| **客户** | client | 最终服务使用者，收到权益后激活并享受养老管家服务 | 权益激活使用、服务评价、需求反馈 |

### 1.4 核心业务流程

#### 流程一：权益采购与寄送

```
渠道/保险公司 → 对公采购权益商品 → 支付 → 权益入库 → 出库寄送给渠道/代理人
                                                              ↓
                                              （渠道/代理人自行赠送给客户，系统不追踪）
```

```
代理人 → 通过专门商城个人采购权益 → 支付 → 权益出库寄送给代理人
                                                    ↓
                                    （代理人自行赠送给客户，系统不追踪）
```

#### 流程二：客户权益激活与管家服务

```
客户收到权益（系统外赠送） → 客户激活权益（系统追踪起点）→ 系统创建服务会话
→ 养老管家受理 → 需求收集（电话/企微）→ 方案定制（电话/企微沟通）→ 管家手动确认方案
→ 全程安排（电话/企微协调）→ 服务执行 → 回访品控（电话/企微回访）
```

#### 流程三：场景活动组织

```
代理人/渠道发起活动 → 选择场景（关联机构） → 预约排期 → 客户邀约 → 活动执行 → 费用结算
```

#### 流程四：渠道系统对接

```
渠道系统 → H5/API对接 → 内容展示/场景展示/权益管理 → 客户触达 → 服务触发
```

| 核心域 | 组织、账号、权限 | 系统域 | 管家域、供应商域、渠道域 |
| 养老管家域 | 管家、排班、评价 | 核心域 | 服务域 |

| 代理人域 | 代理人、业绩 | 渠道域 | 权益域、订单域 |
| 客户域 | 客户、健康档案、需求 | 无 | 服务域、权益域 |
| 权益域 | 权益模板、库存、激活 | 商品域 | 服务域 |
| 服务域 | 需求、方案、安排、回访 | 权益域、客户域 | 订单域 |

| 课程域 | 课程、讲师、学习记录 | 无 | 商品域、订单域 |
| 订单域 | 各类订单、支付、退款 | 权益域、服务域 | 结算域 |
| 结算域 | 流水、账单、发票 | 订单域 | 无 |

## 二、整体设计原则

### 2.1 命名规范

#### 表命名规范

| 规则 | 示例 | 说明 |
|------|------|------|
| 域名前缀 | `system_`、`organ_`、`park_` | 表名以所属业务域为前缀 |
| 小写+下划线 | `park_room_type` | 全部小写，单词间用下划线分隔，不使用缩写（`config`/`sku`/`vr` 为约定缩写除外） |
| 业务实体命名 | `park_info`、`client_info` | 核心实体表统一用 `_info` 后缀；权益/服务等以业务名词命名的核心实体可用 `_template`/`_session` 等更具体的后缀 |
| 关联表命名 | `agent_client_rel` | 多对多关联表用 `_rel` 后缀 |
| 日志/配置/记录表 | `system_log_login`、`system_config`、`channel_config_content`、`content_record_read` | 统一用 `{domain}_log_*` / `{domain}_config_*` / `{domain}_record_*` 后缀形式；跨域集中管理的审计日志用 `system_log_{domain}_*`（如 `system_log_organ`） |
| 关系对照表 | `organ_role_permission_ship` | 用 `_ship` 后缀 |

> **前缀词源说明**：`organ_` = 公司/组织（平台运营方），`park_` = 养老机构/园区（被服务设施），`finance_` = 财务/结算（含支付、退款、流水、账单、发票、应收）。

#### 字段命名规范

| 规则 | 示例 | 说明 |
|------|------|------|
| 主键 | `id` | 统一使用 `bigint`（雪花ID，应用层 SnowflakeId 生成，无 AUTO_INCREMENT） |
| 外键 | `park_code`、`channel_code` | 统一用 `{entity}_code` 业务编码关联 |
| 编码 | `organ_code`、`park_code` | `{entity}_code`，业务编码 |
| 名称 | `full_name`、`short_name` | 主实体表统一用 `full_name`/`short_name` |
| 状态 | `status` | `tinyint`，配合字典表 |
| 类型 | `room_type`、`care_type` | `tinyint`，配合字典表 |
| 金额 | `total_amount`、`unit_price` | `decimal(12,2)` |
| 时间 | `start_time`、`end_time` | `datetime` |
| 日期 | `birthday`、`effective_date` | `date`，统一用全拼 `effective_date`（不用 `effect_date`） |
| 布尔（状态型） | `is_default`、`is_active`、`is_published` | `tinyint(1)`，0=否，1=是；表示「是否处于某状态」用 `is_` 前缀 |
| 布尔（配置型） | `has_wifi`、`has_bathroom` | `tinyint(1)`，0=无，1=有；表示「是否配备某设施/能力」用 `has_` 前缀 |
| 第三方账号 | `open_id`、`union_id`、`alipay_id` | 统一用 `_id` 后缀，单词间用下划线 |
| 操作人 | `operator_code`、`operator_name` | 统一用 `operator_*` 表示「执行操作的人」 |
| 描述 | `remark`、`description` | 统一用全拼 `description`（不用 `_desc` 缩写） |
| 排序 | `sort_order` | `int`，数值越小越靠前 |

#### 通用审计字段（所有表必须包含）

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `created_at` | datetime NOT NULL | 创建时间，默认 CURRENT_TIMESTAMP |
| `updated_at` | datetime NOT NULL | 更新时间，ON UPDATE CURRENT_TIMESTAMP |
| `deleted_at` | datetime NULL | 软删除时间（逻辑删除） |
| `creator` | varchar(50) NULL | 创建人标识 |
| `updater` | varchar(50) NULL | 更新人标识 |

> **接口标识约定**：与外键设计一致，**对外接口/页面跳转/前后端交互中识别业务实体统一使用 `{entity}_code` 业务编码**（如 `parkCode`、`equityCode`、`channelCode`、`sessionCode`、`orderNo`），**不暴露内部 `id` 自增主键**。`id` 仅作为数据库内部主键与日志关联使用，不进入 URL 路径、查询参数、请求体业务字段或前端路由。三类例外：① 翻页游标；② 与第三方系统对接且对方仅支持 ID 的妥协场景（须经待决议清单登记）；③ 暴露给后端运维的非业务资源定位。

### 2.3 RBAC权限模型

本平台采用统一的RBAC（基于角色的访问控制）权限模型，适用于四类账号体系：
- 核心账号（organ_account）：平台运营方
- 养老管家账号（butler_account）
- 供应商账号（supplier_account）
- 渠道账号（channel_account）

**权限分类**：

| 权限类型 | 值 | 说明 |
|---------|---|------|
| 菜单权限 | 1 | 控制页面/菜单可见性 |
| 按钮权限 | 2 | 控制页面内按钮操作 |
| 接口权限 | 3 | 控制API接口访问 |
| 数据权限 | 4 | 控制数据可见范围 |

**数据权限四级**：1=全部 / 2=本部门及下级 / 3=本部门 / 4=仅本人

**各角色域RBAC表统一结构**：

| 表名 | 说明 |
|------|------|
| `{domain}_account` | 账号表 |
| `{domain}_role` | 角色定义表 |
| `{domain}_permission` | 权限定义表 |
| `{domain}_role_permission_ship` | 角色-权限关联表 |
| `{domain}_account_role_rel` | 账号-角色关联表 |
| `{domain}_role_menu_rel` | 角色-菜单关联表（仅核心域） |

### 2.4 状态字段字典规范

| 业务域 | 字典类型 | 状态值 | 说明 |
|--------|---------|--------|------|

## 三、四端功能架构

### 3.1 端定位与账号体系

| 端 | 使用对象 | 部署形态 | 后端账号体系 | 前端工程 |
|----|---------|---------|------------|---------|
| **Admin** 平台后台 | 大雁内部运营/管家/管理员 | Web | organ_account / butler_account | dayan-admin-web (Vue3) |
| **Channel** 渠道后台 | 保险公司管理员/营销/培训 | Web | channel_account | dayan-channel-web (Vue3) |
| **Supplier** 供应商后台 | 供应商（养老机构/服务提供商/设备商） | Web（暂不实现） | supplier_account | dayan-supplier-web（预留） |
| **Distributor** 分销商后台 | 分销商（外部商务合作方） | Web（暂不实现） | distributor_info（当前无 account 表，仅记录归属；distributor-api 预留） | dayan-distributor-web（预留） |
| **Agent** 代理人端 | 保险代理人 | H5 / 小程序 / APP | agent_account（按渠道隔离，同一代理人多渠道） | dayan-agent-app (uniapp) |
| **Client** 客户端 | 保险客户/老人/家属 | 小程序 / H5 | client_account（按渠道隔离，同一客户多渠道） | dayan-client-app (uniapp) |
| **Open** 开放平台 | 外部系统对接（渠道系统/第三方） | API（无独立前端） | app_key / 签名认证 | （无前端，复用 open-api） |

> **端独立性说明**：Channel、Supplier、Distributor、Agent、Client、Admin 六类业务系统在架构上各自独立，分别对应独立的后端账号体系与 API 前缀（`/channel-api/` / `/supplier-api/` / `/distributor-api/` / `/agent-api/` / `/client-api/` / `/admin-api/`），外加 `/open-api/` 开放平台端（外部系统对接，签名认证），共 7 端。供应商与分销商不依附于渠道端管理。当前先实现 Channel/Agent/Client/Admin 四端前端；Supplier/Distributor 前端暂不实现，相关管理操作由 Admin 后台代管（走 admin-api），后端已预留 supplier-api / distributor-api 独立路径，待业务成熟后独立为 dayan-supplier-web / dayan-distributor-web。
>
> **代理人/客户端按渠道隔离**：代理人/客户的信息（agent_info / client_info）与账号（agent_account / client_account）**均按渠道隔离**——每个渠道的代理人/客户都是独立个体（信息可重复存在），同一真实人员/老人在不同渠道可各有一条记录。手机号/微信不要求全局唯一。登录与数据可见性由「账号 + 渠道」共同决定：**前端需支撑登录时选渠道**——手机号/微信登录时，后端按手机号/open_id 检索关联的所有渠道，多渠道时由用户选择（`GET /{端}-api/v1/auth/channels`），选定后登录锁定该渠道。代理人/客户亦可经 ext_account_no（渠道本身账号系统编码）登录。详见数据库 §3.8.2 / §3.9.2。

### 3.4 Supplier 供应商系统（独立，前端暂不实现）

> **定位**：Supplier 是与 Channel 平级的独立系统，服务对象为供应商（养老机构运营方/服务提供商/设备供应商），后端预留独立 `supplier-api` 前缀与 `supplier_account` 账号体系。

| 维度 | 说明 |
|------|------|
| 系统标识 | supplier（supplier_account / supplier-api / dayan-supplier-web 预留） |
| 独立性 | 与渠道逻辑解耦，不归属 Channel 端管理；供应商数据归 supplier 域，渠道仅以只读引用方式查看合作供应商 |
| 功能范围（设计预留） | 供应商入驻、资质与合同管理、机构/服务资源维护、开放平台对接、供应商评价与对账 |
| 当前实现 | 前端（dayan-supplier-web）**暂不实现**，供应商相关管理操作由 **Admin 后台代管**（通过 admin-api 调用 supplier 域表：supplier_info / supplier_account / supplier_contract / supplier_evaluation / supplier_contact 等，详见 §5.4） |
| 后续演进 | 业务量成熟后独立为 dayan-supplier-web + supplier-api，从 Admin 代管中剥离 |

> **与渠道的关系**：渠道（Channel）是采购方，供应商（Supplier）是服务资源提供方，二者在业务上通过订单/服务会话关联，但在系统架构上完全独立，渠道端不做供应商的入驻/审核/合同管理。

### 3.5 Distributor 分销商系统（独立，前端暂不实现）

> **定位**：Distributor 是与 Channel 平级的独立系统，服务对象为分销商（外部商务合作方），后端预留独立 `distributor-api` 前缀。当前仅有 distributor_info（记录渠道归属，无独立 account 表），将来需要分销商自助管理时再补 distributor_account 账号体系。

| 维度 | 说明 |
|------|------|
| 系统标识 | distributor（当前仅 distributor_info，无 account 表；distributor-api / dayan-distributor-web 预留） |
| 独立性 | 与渠道逻辑解耦，**不是渠道的子角色**，不归属【渠道管理】菜单；分销商与渠道通过"渠道归属关系"关联，但各自为独立系统 |
| 核心职责 | 记录其引入的渠道归属关系（distributor_info ↔ channel_info），用于结算佣金 |
| 功能范围（设计预留） | 分销商入驻与资质、渠道归属关系维护、佣金结算与对账 |
| 当前实现 | 前端（dayan-distributor-web）**暂不实现**，分销商相关管理操作由 **Admin 后台代管**（通过 admin-api 调用 distributor 域表：distributor_info，详见 §5.17）。Admin【平台底层】的"分销商管理"入口为代管入口 |
| 后续演进 | 业务量成熟后独立为 dayan-distributor-web + distributor-api，从 Admin 代管中剥离 |

> **与渠道的关系**：分销商与渠道是"引入归属"关系——一个分销商可引入多个渠道，一个渠道归属一个分销商（记录于 channel 维度的归属字段或 distributor↔channel 关联）。该关系用于结算域计算佣金（见 §5.16、§9.4），但分销商不参与渠道内部业务操作，也不是渠道的子菜单。

## 四、核心业务流程数据流

### 4.1 权益采购与出库流程

```
1. 渠道对公采购下单
   channel_info → order_equity（创建权益订单，状态=0待支付）
   ↓
2. 渠道支付（对公转账/银行转账）
   order_equity.order_status → 1（已支付）
   finance_flow（创建财务流水：渠道支出/平台收入）
   ↓
3. 权益批量生产入库
   equity_template → equity_batch（创建批次）
   equity_depot（批量生成权益卡/函，状态=0库存中）
   equity_depot.batch_code → 关联批次
   ↓
4. 权益出库寄送
   equity_depot.outbound_channel_code → 接收渠道编码
   equity_depot.outbound_agent_code → 接收代理人编码（可选）
   equity_depot.equity_status → 1（已出库）
   equity_depot.outbound_time → 出库时间
   equity_depot.logistics_no → 物流单号
   equity_batch.outbound_count + N
   ↓
5. 渠道/代理人收到权益后自行赠送给客户
   （此过程在系统外完成，系统不追踪赠送过程）
```

**涉及表**：order_equity, goods_info, goods_sku_equity, finance_flow, equity_template, equity_batch, equity_depot, finance_bill

### 4.2 客户权益激活与管家服务流程

```
1. 客户激活权益（系统可追踪的起点）
   equity_activate（创建激活记录）
   equity_depot.equity_status → 2（已激活）
   equity_depot.activate_time = 当前时间
   equity_depot.expire_time = 当前时间 + valid_days
   equity_depot.client_code → 客户编码
   equity_use_person（登记使用人信息）
   ↓
2. 系统自动创建服务会话
   service_session（创建服务会话，状态=1待分配）
   ↓
3. 管家受理 → 需求收集（通过电话/企微与客户沟通）
   service_session.session_status → 2（处理中）
   service_equity_demand（创建需求记录）
   client_health_profile（更新/创建健康档案）
   client_care_need（创建照护需求评估）
   ↓
4. 管家定制方案（通过电话/企微与客户沟通方案）
   service_session.session_status → 3（方案待确认）
   service_equity_solution（创建方案，关联park_info推荐机构）
   ↓
5. 管家确认方案（电话/企微沟通后，管家在系统中手动标记确认）
   service_session.session_status → 4（服务安排中）
   写入参访/入住安排信息
   ↓
6. 管家全程安排（电话/企微协调资源）
   service_equity_arrange（创建安排记录）
   ↓
7. 服务执行
   service_session.session_status → 5（服务中）
   equity_depot.equity_status → 3（使用中）            ← 首次进入服务执行
   equity_depot.first_use_time = 当前时间（首次使用时写）
   butler_service_record（记录服务过程，communicate_way标记电话/企微）
   ↓
8. 回访品控（电话/企微回访）
   service_session.session_status → 6（已完成）
   service_equity_followup（创建回访记录）
   service_evaluation（创建评价记录）
   equity_depot.equity_status → 4（已完成）
   equity_depot.use_count + 1
```

**涉及表**：equity_depot, equity_activate, equity_use_person, service_session, service_equity_demand, client_health_profile, client_care_need, service_equity_solution, park_info, service_equity_arrange, butler_service_record, service_equity_followup, service_evaluation, butler_rating

### 4.3 场景活动组织流程

```
1. 渠道/代理人浏览场景
   scene_info（查询可预约场景）
   scene_schedule（查询可预约时间段）
   content_record_read（记录浏览记录）
   ↓
2. 选择场景预约
   order_scene（创建场景订单，状态=0待支付）
   ↓
3. 支付确认
   order_scene.order_status → 1（已支付）
   finance_flow（财务流水）
   ↓
4. 场景排期确认
   scene_schedule.current_person + 参与者数
   scene_schedule.status → 2（已约满，如果满员）
   ↓
5. 活动执行
   butler_service_record（管家服务记录）
   scene_resource（资源使用情况）
   ↓
6. 活动完成
   order_scene.order_status → 4（已完成）
   service_evaluation（活动评价）
```

### 4.4 渠道系统对接流程

```
1. 渠道接入配置
   channel_info（创建渠道信息）
   channel_open_platform（配置对接参数：app_key, app_secret, 回调地址等）
   ↓
2. 渠道内容配置（大雁生产内容，渠道按 app_type=agent/client 配置下游两端各展示哪些）
   channel_config_content（渠道配置展示内容，app_type 区分保典端 agent / 客平端 client）
   channel_config_scene（渠道配置展示场景，app_type 区分两端）
   channel_config_goods（渠道配置可售商品，app_type 区分两端）
   ↓
3. 系统认证对接
   channel_open_platform（Token认证/签名验证）
   system_log_channel（记录对接日志）
   ↓
4. 权益数据同步
   equity_depot → 通过API推送权益数据到渠道系统
   equity_activate ← 接收渠道系统的激活回调
   channel_data_sync_log（记录同步日志）
   ↓
5. 数据对账
   finance_reconciliation（定期与渠道对账）
```

### 4.5 养老机构入驻流程

```
1. 供应商入驻
   supplier_info（创建供应商信息，状态=0待审核）
   supplier_account（创建账号）
   ↓
2. 平台审核
   supplier_info.audit_status → 1（审核通过）
   supplier_info.status → 1（已合作）
   system_log_organ（记录审核日志）
   ↓
3. 合同签署
   supplier_contract（创建合同）
   ↓
4. 机构信息录入
   park_info（创建机构信息，状态=0待审核）
   park_media_*（多媒体资源，4张表）
   park_room_type + park_room_price（房间信息）
   park_care_type + park_care_price（照护信息）
   park_food_type + park_food_price（餐饮信息）
   ↓
5. 机构审核上线
   park_info.published → 1（已发布上线）
   ↓
6. 定期探访评估
   service_visit_record（管家探访记录）
   supplier_evaluation（供应商评估）
```

### 4.6 结算流程

```
1. 流水归集
   finance_flow（所有交易产生的流水自动归集）
   ↓
2. 生成结算单（结算单=应收概念）
   finance_bill（按结算周期生成结算单，代表应向渠道/分销商收取的款项）
   finance_bill.flow_ids ← 关联流水
   ↓
3. 审核确认
   finance_bill.bill_status → 1（审核通过）
   ↓
4. 执行结算
   finance_bill.bill_status → 3（已结算）
   finance_flow（结算收款流水）
   ↓
5. 开具发票
   finance_invoice（根据结算单开票）
   ↓
6. 对账确认
   finance_reconciliation（定期对账）
```

## 六、服务会话状态机详细转移矩阵

> 服务会话采用 `(session_status, sub_status)` 二维状态机，状态转移规则配置于 `system_state_machine` 的 `SERVICE_SESSION_SM`，运营可调。完整转移矩阵共 20+ 条规则，下表穷举核心 18 条 + 2 条 anyStatus 规则。
>
> **重要说明**：养老管家通过电话或企业微信与客户对接服务，所有状态流转由管家在Admin后台手动操作。客户在客户端为只读（查看服务进度），不参与状态变更操作。

### 6.1 主状态（session_status）

| 值 | 名称 | 说明 |
|---|------|------|
| 1 | 待分配 | 等待管家分配 |
| 2 | 处理中 | 需求收集阶段 |
| 3 | 方案待确认 | 方案定制完成，管家通过电话/企微与客户沟通后手动确认 |
| 4 | 服务安排中 | 安排中（待入住/待参访） |
| 5 | 服务中 | 服务执行中 |
| 6 | 已完成 | 终态 |
| 7 | 已取消 | 终态 |

### 6.2 子状态（sub_status）

| 值 | 名称 |
|---|------|
| normal | 正常 |
| hold | 挂起 |
| urgent | 紧急 |
| reassign | 改派 |
| refund_review | 退款审核 |
| refund_done | 退款完成 |
| interrupted | 中断 |

### 6.3 转移矩阵

| fromStatus | fromSubStatus | action | toStatus | toSubStatus | 备注 |
|------------|---------------|--------|----------|-------------|------|
| 1 待分配 | normal | assign | 2 处理中 | normal | 写 assign_time |
| 1 待分配 | normal | cancel | 7 已取消 | normal | 未扣减次数 |
| 1 待分配 | normal | timeout | 1 待分配 | urgent | 升级+通知主管 |
| 2 处理中 | normal | submitScheme | 3 方案待确认 | normal | - |
| 2 处理中 | normal | reassign | 2 处理中 | reassign | 转单成功回 1 待分配 |
| 2 处理中 | normal | hold | 2 处理中 | hold | 记录挂起原因 |
| 2 处理中 | hold | resume | 2 处理中 | normal | 解除挂起 |
| 3 方案待确认 | normal | confirmScheme | 4 服务安排中 | normal | 管家电话/企微沟通后手动确认，写入参访/入住安排 |
| 3 方案待确认 | normal | rejectScheme | 2 处理中 | normal | 方案 version+1 重制 |
| 3 方案待确认 | normal | refundApply | 3 方案待确认 | refund_review | 进入退单审核 |
| 3 方案待确认 | refund_review | refundPass | 3 方案待确认 | refund_done | 返还次数，终态 |
| 4 服务安排中 | normal | startServe | 5 服务中 | normal | - |
| 5 服务中 | normal | finish | 6 已完成 | normal | 触发扣减，写 finish_time |
| 5 服务中 | normal | interrupt | 5 服务中 | interrupted | 等待恢复 |
| 5 服务中 | interrupted | resume | 5 服务中 | normal | - |
| 5 服务中 | normal | terminate | 7 已取消 | normal | 终止服务 |
| 任意非终态 | normal | markUrgent | (原status) | urgent | SLA 压缩 50% |
| 任意非终态 | urgent | unmarkUrgent | (原status) | normal | - |
| 任意非终态 | normal | hold | (原status) | hold | 挂起期间不计SLA |
| 任意非终态 | hold | resume | (原status) | normal | - |

### 6.4 实现要点

- **状态校验入口统一**：`ServiceSessionStateMachine.transition(sessionCode, action)`，禁止应用层直接 UPDATE status
- **终态校验**：status=6/7 或 sub_status=refund_done 不可再转移
- **hold 与 urgent 同时存在时以 hold 优先**（挂起期间不计SLA）
- **SLA计时**：基于状态转移记录计算每段耗时，紧急(urgent)压缩50%，挂起(hold)期间暂停计时
- **配置化**：所有转移规则在 `system_state_machine` 表中可配置，应用启动时缓存，DB变更时刷新
- **操作方统一为管家**：所有状态流转操作由管家在Admin后台执行，客户端仅查看进度

## 九、业务规则说明

### 9.1 权益生命周期规则

```
权益状态流转：

  [系统管控范围外]                    [系统管控范围内]
  库存中(0) ──出库寄送──→ 已出库(1) ──客户激活──→ 已激活(2)
    │                       │                        │
    │                       │                        ↓
    │                       │                  使用中(3) ──完成──→ 已完成(4)
    │                       │                                    │
    └──作废──→ 已作废(6)    └──货架过期(shelf_expire_time)──→ 已过期(5)
                              ↓                                    ↑
                          客户激活                               过期
                          （未激活过期由定时任务扫描 shelf_expire_time 触发）
    库存中(0) ──货架过期(shelf_expire_time)──→ 已过期(5)

  特殊流转：
  - 已激活(2) → 更换权益人中(7) → 已激活(2)（更换完成后恢复，激活后才可更换）
  - 已激活(2) → 已作废(6)（特殊场景，如客户注销）
  - 使用中(3) / 已完成(4) → 已过期(5)（expire_time 到期由定时任务触发）
```

**关键规则**：

1. 权益激活时自动计算过期时间：`expire_time = activate_time + valid_days`
2. 未激活权益在 `shelf_expire_time` 到期后自动变为已过期
3. 可更换权益人的权益，在更换期间（status=7），原权益人暂停使用，更换完成后恢复
4. 权益使用次数达到 `max_use_count` 后自动变为已完成
5. 权益出库只记录寄送对象（渠道/代理人）和物流单号，不追踪最终客户
6. 客户激活是系统可追踪的起点，激活时绑定客户信息和使用人信息

### 9.2 订单生命周期规则

```
订单状态流转（以权益订单为例）：
  待支付(0) ──支付成功──→ 已支付(1) ──部分出库──→ 部分发放(2) ──全部出库──→ 已发放(3)
    │                                                              │
    │                                                         服务完成
    │                                                              │
    │                                                         已完成(4)
    │
    超时取消──→ 已取消(5)
    支付失败──→ 已取消(5)

  退款流转：
  已支付(1)/部分发放(2) ──申请退款──→ 退款中(6) ──退款成功──→ 已退款(7)
```

**关键规则**：

1. 订单创建后30分钟未支付自动取消（可通过系统配置调整）
2. 支付成功后触发权益出库流程
3. 批量出库的订单支持部分发放状态（部分权益已出库寄送，其余待出库）
4. 退款需要在权益全部激活前发起，已激活的权益不支持退款
5. 订单状态流转由 `system_state_machine` 的 ORDER_SM 驱动，禁止应用层绕过；非法状态变更抛业务异常
6. 通过 `order_source` 区分渠道对公采购（1）和代理人个人采购（2），两种采购模式共用同一张订单表

### 9.3 服务流程规则

```
服务会话状态流转（与 §6 状态机一致）：
  待分配(1) ──assign──→ 处理中(2) ──submitScheme──→ 方案待确认(3) ──confirmScheme──→ 服务安排中(4)
                                                                    │
                                                       startServe──→ 服务中(5)
                                                                    │
                                                       finish────→ 已完成(6) [终态]
                                                                    │
                                                       cancel/terminate──→ 已取消(7) [终态]

  子状态（sub_status）叠加：normal / hold(挂起) / urgent(紧急) / reassign(改派)
                            / refund_review(退款审核) / refund_done(退款完成) / interrupted(中断)
```

**关键规则**：

1. 权益激活后自动创建服务会话（session_status=1 待分配），管家需在2小时内受理（超时 timeout 转 sub_status=urgent 升级）
2. 需求收集阶段需完成健康档案建立/更新（client_health_profile）
3. 方案定制至少提供1个推荐方案，建议提供2-3个备选（service_equity_solution）
4. 方案确认由管家执行：管家通过电话/企微与客户沟通方案后，在Admin后台手动操作 confirmScheme，将状态从「方案待确认」推进到「服务安排中」
5. 安排阶段需与客户确认时间和细节（service_equity_arrange.is_confirmed=1 后方可 startServe）
6. 服务完成后7天内必须完成回访（service_equity_followup）
7. 回访评分低于3分的需要创建跟进记录
8. 服务会话状态由 `(session_status, sub_status)` 二维状态驱动，状态转移规则配置于 `system_state_machine`（SERVICE_SESSION_SM），禁止应用层绕过状态机直接 UPDATE
9. 同一服务期内，一个客户仅能绑定一位管家（butler_client_rel）；解绑后允许重新分配
10. 客户发起退单（refundApply）经 refund_review 审核通过（refundPass）后，sub_status=refund_done 终态，需返还权益使用次数

**服务四环节操作方与交互方式**：

| 环节 | 操作方 | 与客户交互方式 | 系统操作 |
|------|--------|--------------|---------|
| ①需求收集 | 管家 | 电话/企业微信 | 管家在Admin录入需求 |
| ②方案定制 | 管家 | 电话/企业微信沟通方案 | 管家在Admin创建方案 → 手动标记已确认 |
| ③全程安排 | 管家 | 电话/企业微信协调 | 管家在Admin记录安排进展 |
| ④回访品控 | 管家 | 电话/企业微信回访 | 管家在Admin填写回访记录 |

### 9.4 结算规则

**关键规则**：

1. 渠道结算按月/季周期生成结算单（结算单=应收概念）
2. 结算金额 = 订单金额 - 退款金额 ± 调整金额
3. 结算单需经财务审核后方可执行收款
4. 供应商结算根据合同约定的结算周期执行
5. 分销商佣金通过分销商归属关系自动核算，纳入对应结算单
6. 对账差异需在5个工作日内处理完毕
7. 订单完成后 T+1 日触发分账，分润比例取合同 > 供应商默认手续费 > 全局默认三级优先级（注：此处"手续费"指渠道/分销商层级的结算分润，非代理人佣金——代理人佣金业务 v4.0 已删除）

### 9.5 权限控制规则

**关键规则**：

1. 超级管理员拥有所有权限，不可删除
2. 角色可继承，子角色自动包含父角色的所有权限
3. 数据权限优先级：全部 > 本部门及下级 > 本部门 > 仅本人
4. 接口权限校验统一处理
5. 菜单权限控制前端页面可见性
6. 按钮权限控制页面内操作可见性
7. 各角色域（organ/butler/supplier/channel）的权限体系独立管理
8. 渠道级功能开关（feature_config）与用户级权限（channel_role）为"与"关系：接口可访问 = 功能已开通(渠道) AND 角色有权限(用户)

### 9.6 内容展示配置规则

**关键规则**：

1. 内容全部由大雁养老生产（Admin端内容素材库管理）
2. 渠道通过Channel端的「内容配置」功能，选择其下游代理人端（Agent端）和客户端（Client端）分别展示哪些内容
3. 渠道只能看到大雁已审核通过的内容，不可自行生产内容
4. 同一内容可被多个渠道选择展示，也可以不被任何渠道选择
5. 渠道配置的内容只对本渠道的代理人和客户可见（数据隔离）
6. Admin端的「内容管理」按 appType 区分代理人端内容和客户端内容，方便运营管理

### 10.3 非功能性需求

#### 10.3.1 性能要求

| 指标 | 目标 | 说明 |
|------|------|------|
| 列表查询 P99 | < 500ms | 权益列表、机构列表、活动列表 |
| 权益激活 P99 | < 200ms | 核心链路，涉及状态变更和事务 |
| 活动报名 P99 | < 500ms | 高并发场景 |
| 登录认证 P99 | < 300ms | Sa-Token + Redis |
| 字典查询 P99 | < 50ms | Redis缓存，key-level partitioned |

**负载基准（性能指标前提）**：10万客户 / 30万权益卡 / 100万服务记录 / 峰值200 QPS

#### 10.3.2 安全要求

| 安全维度 | 要求 | 说明 |
|---------|------|------|
| 敏感数据 | 脱敏展示，AES加密存储 | 身份证号、手机号、银行账号、密码 |
| 密码 | BCrypt加盐哈希 | 不可逆 |
| Token | 2小时有效，续期支持 | Sa-Token统一管理 |
| 登录安全 | 错误5次锁定30分钟 | 防暴力破解 |
| 接口安全 | 全量鉴权 + Sentinel限流 | 按端隔离token命名空间 |
| 操作审计 | 所有写操作记录日志 | system_operation_log + 各域 log表 |
| 多租户隔离 | 渠道间数据逻辑隔离 | channel_code字段级过滤，CI纳入回归测试 |
| 支付安全 | 签名验证 + 回调验签 | 金额以"分"为单位，大额>5000元人工审核 |

#### 10.3.3 可用性要求

- 权益激活、活动报名、定时任务（SLA升级、权益过期扫描）为关键链路
- 对账任务每日03:00执行，不一致告警
- 消息推送5分钟重试，不超过3次
- Redis Cluster + MySQL主从保障数据高可用

#### 10.3.4 审计与合规

- 所有写操作记录 `system_operation_log`（含IP/UA/参数/结果/trace_id）
- 敏感数据变更全量留痕
- 渠道数据源隔离，防止A渠道访问B渠道数据
- 定期安全审计 + 依赖漏洞扫描

### 10.5 v4.0 相对于 v3.0 的主要变更摘要

| 变更项 | v3.0 | v4.0 | 变更原因 |

| 客户采购权益 | 存在客户采购入口 | 明确客户不参与权益采购，仅渠道对公/代理人个人 | 权益采购边界 |

| 审计日志分散 | client_login/service_change/order_status 散落各域 | 集中到 system 域统一前缀 | 审计集中管理 |
