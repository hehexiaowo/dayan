## 一、整体架构现状（对照 `03 系统架构设计文档`）

### 1.1 后端工程结构（实际）

实际为 `dayan-server/` Maven 多模块工程（设计文档 03 称父项目为 `dayan-platform`、06 称 `dayan-server`，**实际为 `dayan-server`**）：

| 分组 | 实际内容 |
|---|---|
| `dayan-common/` | **12 个**基础模块：`bom`、`core`、`mybatis`、`redis`、`security`、`log`、`oss`、`sms` 已实现；`mq`、`lbs`、`pay`、`swagger` 为占位（仅 `package-info`） |
| `dayan-modules/` | **17 个**业务域模块（与设计一致） |
| `dayan-starters/` | **6 个** Spring Boot 启动器（见 1.2） |
| `dayan-gateway/` | Spring Cloud Gateway，端口 **8000** |
| `dayan-job/` | 定时任务，端口 **8090**（见 1.3） |

> 设计文档 03 列 8 个公共模块、06 列 11 个，均不完整。实际为 12 个（含 `bom`）。

### 1.2 启动器与端口（实际）

| 启动器 | 端口 | context-path | 状态 |
|---|---|---|---|
| `dayan-admin` | 8080 | `/admin-api` | ✅ 已实现（接入全部 17 模块） |
| `dayan-channel` | 8081 | `/channel-api` | ✅ 已实现（9 模块） |
| `dayan-agent` | 8082 | `/agent-api` | ✅ 已实现（10 模块） |
| `dayan-client` | 8083 | `/client-api` | ✅ 已实现（10 模块） |
| `dayan-supplier` | 8084 | `/supplier-api` | ⏸ 预留（前端未实现） |
| `dayan-distributor` | 8085 | `/distributor-api` | ⏸ 预留（前端未实现） |

每个 Controller 按**受众端**拆分（`controller/admin|channel|agent|client`），由各启动器按端依赖裁剪装载。技术栈：Spring Boot + Spring Cloud Alibaba（Nacos 服务发现/配置）+ MyBatis-Plus + Sa-Token + Druid。

### 1.3 调度框架 ⚠️ 重要修正

**设计文档自相矛盾**：`06 项目开发规范` §1.1 写 `dayan-job` = "XXL-Job/Quartz 执行器"；`03 系统架构` 写 Spring `@Scheduled` + 分布式锁。

**实际现状：Spring `@Scheduled`（`@EnableScheduling`）。未使用 Quartz，未使用 XXL-Job**（`DayanJobApplication` Javadoc 注明"未来可切 XXL-Job"，属预留扩展点）。全工程无 `org.quartz` / `SchedulerFactory` / `com.xxl` 依赖。

`dayan-job` 内 5 个调度器：

| 调度器类 | Cron | 职责 |
|---|---|---|
| `OrderTimeoutScheduler` | 每 5 分钟 | 待支付订单超时取消（ORDER_SM） |
| `EquityExpireScheduler` | 每小时 | 权益上架过期 + 激活态过期（EQUITY_SM） |
| `QuotaResetScheduler` | 每年 1-1 00:00 + 启动补跑 | 年度配额重置（`resetAnnualQuota`） |
| `ReconciliationScheduler` | 每日 03:00 | `finance_flow` vs `finance_bill` 按渠道对账 |
| `ServiceSlaScheduler` | 每小时 | 服务 SLA：待处理>2h→`urgent`；7 天缺回访告警 |

> Quartz 方案曾尝试接入，后因 Spring Boot 配置冲突**回滚废弃**，改用轻量 Spring 原生调度。

### 1.4 消息队列（设计→落地差异）

设计文档 03 选型 RocketMQ 5.1.x，06 `dayan-common-mq` 注释写"RabbitMQ/RocketMQ"二选一。

**实际：`dayan-common-mq` 为占位模块（仅 `package-info`），未实际接入任何 MQ。** 当前跨域异步逻辑通过事务事件（`@TransactionalEventListener(AFTER_COMMIT)`）+ 本地调度实现，无外部 broker 依赖。

### 1.5 前端四端（实际）

| 目录 | 框架 | UI 库 | 开发端口 | 页面规模 |
|---|---|---|---|---|
| `dayan-admin` | Vue 3 + Vite（Web） | Element Plus | 5173 | ~105 页面 |
| `dayan-channel` | Vue 3 + Vite（Web） | Element Plus | 5174 | ~31 页面 |
| `dayan-agent` | uni-app（H5/小程序）+ Vue 3 | uview-ui | 5182 | ~46 页面 |
| `dayan-client` | uni-app（H5/小程序）+ Vue 3 | uview-ui | 5183 | ~33 页面 |

> supplier / distributor 前端未实现，与设计一致。Web 端共享 `api/components/composables/layouts/router/stores/utils` 结构；uni-app 端用 `manifest.json + pages.json + pages/`。

### 1.6 文件存储（设计→已落地）

设计文档 03 §5.6 方案（MinIO 为主 + OSS/COS 备选 + 预签名直传）已落地：`dayan-common-oss` 实现 MinIO **后端流式中转上传 + 代理下载/显示**；DB 存纯 key；admin 端 25 页接入，channel/agent/client 端修复了显示链路。

## 二、数据库结构变更（对照 `02 数据库设计文档 v4.1`）

### 2.1 总览

设计基线 **127 表 / 17 域**。实际现状 **129 表**（净增 2）。变化集中在 5 个域：

| 业务域 | 设计(v4.1) | 实际 | 净变化 |
|---|---|---|---|
| park | 15 | 13 | **−2**（大重构） |
| equity | 6 | 5 | **−1**（模板废除） |
| goods | 5 | 6 | **+1**（SKU 重构） |
| service | 7 | 8 | **+1**（+服务项目+配额） |
| agent | 6 | 8 + `learning_content` | **+3**（线索+学习） |
| 其余 12 域 | — | 不变 | 0 |

> 其余域（system 18 / organ 9 / butler 8 / supplier 10 / scene 5 / channel 11 / client 7 / content 5 / course 3 / order 4 / finance 7 / distributor 1）表数量与设计一致，仅个别列有调整。

### 2.2 park 域 — 15 → 13（重大重构）

**核心思路：用"统一表 + 类型字段"替代设计文档中"一类资源一张表"的散表方案。**

| 设计文档(v4.1) | 实际现状 | 变更 |
|---|---|---|
| `park_media_image` / `park_media_video` / `park_media_file` / `park_media_vr`（4 张） | `park_asset` | **合并**（`asset_type` 1图/2视频/3文件/4VR + 来源追踪） |
| `park_room_price` / `park_care_price` / `park_food_price` + facility/service 价格（5 张） | `park_pricing` + `park_pricing_item` | **合并**（`charge_type` 区分；明细进 `park_pricing_item`） |
| `park_facility` | `park_facility_type` | **改名** |
| `park_service_item` | `park_service_type` | **改名** |
| `park_info.score_*`（评分内嵌） | `park_score` | **拆表**（独立评分表 + 乐观锁） |
| `park_care_type` / `park_food_type` | 保留不变 | — |
| —（新增） | `park_display_block` | **新增**（C 端详情页通用展示板块：`block_type`+标题+富文本+JSON 图片数组，替代远程库"加列"灾难） |

`park_info` 关键列调整：`score_*` 移出；`longitude`/`latitude` 改 `DECIMAL(10,6)`；新增 `network_tags`（逗号分隔，FIND_IN_SET 查询）、`vital_config`/`care_config`/`sojourn_config`（TEXT JSON 展示配置）。

**实际 park 表（13）**：`park_info`、`park_asset`、`park_facility_type`、`park_service_type`、`park_adviser`、`park_periphery`、`park_room_type`、`park_pricing`、`park_pricing_item`、`park_score`、`park_care_type`、`park_food_type`、`park_display_block`。

### 2.3 equity 域 — 6 → 5（equity_template 废除）

**核心思路：废除"权益模板"概念，权益属性改由"商品配置 + 服务项目"驱动。**

- **`equity_template` 已 DROP**（`23_drop_legacy.sql`）。
- 替代：`goods_equity`（商品级 1:1 权益配置）+ `service_item`（原子服务能力）+ `goods_service_item_rel`（商品↔服务项目 N:M，见 goods 域）。
- **激活链路改键**：`equity_batch` / `equity_depot` / `equity_activate` 的 `template_code` → **`goods_code`**（`22_equity_link_refactor.sql`）。
- `equity_depot` 列调整：删除 `equity_type`/`equity_value`/`use_count`/`max_use_count`；新增 `person_count`/`valid_days`（激活时从 `goods_equity` 快照）。
- `equity_use_person.use_person_id_card` `VARCHAR(20)` → `VARCHAR(128)`（AES-256-GCM 密文 64 字符，`36_widen_encrypted_id_card.sql`）。

**实际 equity 表（5）**：`equity_batch`、`equity_depot`、`equity_activate`、`equity_use_person`、`equity_change_holder`。

> ⚠️ 全库 AES-GCM 加密列陷阱：`id_card`/`phone` 等 PII 列按明文 `varchar(20)` 建表，但密文需 64 字符。`use_person_id_card` 已扩容，其余列未来加密时同样需扩容至 `varchar(128)`。

### 2.4 goods 域 — 5 → 6（SKU 重构）

| 设计文档(v4.1) | 实际现状 | 变更 |
|---|---|---|
| `goods_sku_equity` | `goods_equity` + `goods_service_item_rel` | **删除并替换** |
| `goods_sku_scene` | `goods_scene` | **改名**（去 `_sku_` 中缀，字段不变） |
| `goods_sku_course` | `goods_course` | **改名** |
| `goods_sku_sojourn` | `goods_sojourn` | **改名** |

`goods_info.goods_type`：1权益 / 2场景 / 3课程 / 4旅居。

**实际 goods 表（6）**：`goods_info`、`goods_equity`、`goods_service_item_rel`、`goods_scene`、`goods_course`、`goods_sojourn`。

### 2.5 service 域 — 7 → 8（+服务项目 + 配额模型）

- **新增 `service_item`**：原子服务能力，`item_category` 1=安排权益 / 2=费用权益；`item_subtype`（仅安排类）1旅居 / 2活力长居 / 3照护长居。
- **配额模型**（`25_quota_model.sql`）：
  - `goods_service_item_rel.quota_type`：**1=终身总量 / 2=年度配额**（年度重置）。
  - `service_session` 新增配额快照列：`max_use_count`（激活时从 `rel.quantity` 冻结）、`used_count`、`quota_type`、`quota_reset_year` + 索引 `idx_quota_reset`。
- `service_session.item_code` 新增；`service_type` 放宽为可 NULL。

**实际 service 表（8）**：`service_session`、`service_item`、`service_equity_demand`、`service_equity_solution`、`service_equity_arrange`、`service_equity_followup`、`service_evaluation`、`service_visit_record`。

### 2.6 agent 域 — 6 → 8（+ `learning_content`）

设计文档仅 6 表，实际已扩展为代理人 CRM + 学习中心：

- **新增 `agent_lead`**：代理人线索（潜在客户 CRM，迁移 28）；后续追加访客追踪列 `visitor_token`/`visitor_source`/`wx_nickname`/`wx_avatar`/`last_trace_time`/`trace_count`/`last_trace_type`（迁移 32/33）。
- **新增 `agent_lead_trace`**：线索互动记录（浏览内容/工具/海报，迁移 32）。
- **新增 `learning_content`**：学习中心内容（视频/图文/雁鸣中国，迁移 34）。**全局表，无 `channel_code`、无 `agent_` 前缀**，须加入租户拦截器忽略清单。

**实际 agent 表**：`agent_info`、`agent_account`、`agent_favorite`、`agent_client_rel`、`agent_performance`、`agent_share_record`、`agent_lead`、`agent_lead_trace` + `learning_content`。

## 三、业务模型与流程变更（对照 `01 产品需求` / `05 API`）

### 3.1 权益生命周期重构

设计文档描述"权益模板 → 批量印刷生成 → 入库"模型。**实际已重构**：
- 废除 `equity_template`，权益属性由 **`goods_equity`（商品配置）+ `service_item`（服务能力）** 驱动。
- 激活链路从 `template_code` 改挂 `goods_code`；`equity_depot` 激活时固化商品快照（`person_count`/`valid_days`）。
- 权益 `equity_type` 仅剩**展示用途**，唯一功能耦合是激活时 `mapEquityTypeToServiceType()` 决定 `service_session.service_type`；订单/履约不依赖。

### 3.2 配额履约模型

- 配额按 `equity + service_item` 聚合统计，不再用 `service_session` 单行 `used_count` 累加（单行固定为 1）。
- 关键修复：① 配额消费须在 `@TransactionalEventListener(AFTER_COMMIT)` 事务边界；② `ensureInUse` 状态防抖。
- client 端发起履约 + `usePersonId` 归属校验；`QuotaResetScheduler` 年度重置。

### 3.3 找机构三网络体系

设计文档未细分。**实际按活力/照护/旅居三网络物理分离**：
- 三目录：**vital（活力·蓝）/ care（照护·橙）/ sojourn（旅居·绿）**，各自独立列表/详情页。
- `park_info.network_tags`（逗号分隔多选）替代原 `ability_type`/`stay_type` 推导，`FIND_IN_SET` 精准查询。
- `vital_config`/`care_config`/`sojourn_config`（TEXT JSON）控制各网络头图/缩略图展示。
- **地图采用 DataV 动态边界 choropleth 热力图**（按 adcode 拉 GeoJSON + `useRegionHeatmap` composable），区县级起接入真实地图，已替换原 `effectScatter` 方案与 4.4MB 静态 GeoJSON 资产。

### 3.4 多方式登录（超出设计）

设计文档仅账号密码。**实际支持三方式登录**：验证码 / 密码 / 微信。
- `dayan-common-sms`（Mock + 开发态验证码）+ Redis 验证码（5min 有效 + 60s 冷却）。
- `identifier` 匹配 `phone`/`username`/`openId`；密码 BCrypt（`$2a$10$`）。
- Sa-Token 白名单 + 登录页 Tab 切换；微信为骨架扩展点。

### 3.5 内容多形式数据模型

`content_info` 支持 `content_type`（1图文/2视频/3图集/6文件）+ `source_type`（原创/转载）+ `content_body`（JSON 约定）；4 种卡片 + 详情按类型布局；`channel_config_content` 控可见性；`agent_favorite` 租户跳过。

### 3.6 Sa-Token 多端架构

单 `StpInterface` bean + SPI dispatcher 实现多端鉴权（多 bean 共存会启动崩）。每端 starter 启动时 `DefaultStpLogicInitializer` 调 `StpUtil.setStpLogic` 注册 `@SaCheckPermission`。client 端不用 `@SaCheckPermission`，权限保护下沉 service 层（`clientCode` 从 Sa-Token session 取）。
